    How questions are built

    Every question is a production problem: “the agent does X wrong 12% of the time, what is the best fix?” All four options sound reasonable. The right one targets the root cause with the smallest, most reliable mechanism. Wrong options are usually one of four types:

    • Probabilistic fix for a deterministic need. “Add it to the system prompt” when a rule must hold every time.
    • Over-engineering. A new classifier, routing layer or model when a better tool description would do.
    • Wrong layer. Fixing subagents when the coordinator's decomposition is the bug.
    • Hiding the problem. Empty results on error, generic “operation failed,” bigger iteration caps.

    The 10 rules that answer most questions

    If you remember nothing else, these ten rules pick the right answer on most questions. Each comes with an exam-style example: the situation, the right fix, and the distractor the exam would tempt you with.

    1. Must-always rules go in code, not prompts.Prompts and few-shot are probabilistic. Hooks, prerequisite gates and schemas are deterministic. Refund limits, identity checks before money moves, and compliance all mean hooks or gates.

      ExamplePolicy says refunds over $500 need a human. The system prompt states this in capitals, yet 3% of chats still issue a $600+ refund.

      Right fixA PreToolUse hook checks every process_refund call, blocks any amount over $500, and routes the case to escalate_to_human.

      Tempting distractorRepeat the limit at the start and end of the system prompt and add few-shot examples of declining large refunds.

    2. Fix the root cause at the right layer.Incomplete research with healthy subagents means coordinator decomposition. Wrong tool picked means tool description. A teammate missing an instruction means a file in the wrong scope.

      ExampleA report on “renewable energy adoption” covers solar and wind in depth but never mentions hydro, geothermal or storage. Logs show every subagent completed its assigned subtask.

      Right fixFix the coordinator's decomposition so the subtasks cover the whole topic. The subagents did exactly what they were asked.

      Tempting distractorTune the search subagent's queries, or give the synthesis agent a bigger context window.

    3. Proportionate beats elaborate.Prefer the smallest change that removes the cause. A new classifier, routing model or rewrite is usually the distractor.

      ExampleThe agent sometimes calls get_customer when a user asks “where is order #48812?” Both tools have one-line descriptions.

      Right fixRewrite the two tool descriptions so each says when to use it and when to use the other. It is a ten-minute change aimed at the cause.

      Tempting distractorTrain a routing classifier that picks the tool before Claude sees the message, or merge both tools into one.

    4. Tool descriptions drive tool selection.State purpose, inputs, examples, edge cases, and when to use it instead of X. Overlapping descriptions cause misrouting.

      Examplelookup_order is described only as “Looks up orders.”

      Right fix“Use when the customer gives an order number (e.g. #12345) or asks about the shipping, return or status of a specific order. Input: order_id string. For account details such as email or address, use get_customer instead.”

      Tempting distractorLeave the description as is and add five few-shot examples of order questions to the system prompt.

    5. Subagents start blank.They inherit no conversation history or memory. Everything they need goes in their prompt, ideally structured (content plus metadata like URL, page, date).

      ExampleThe search subagent found 12 sources. The synthesis subagent then writes a report that cites none of them.

      Right fixThe coordinator passes the search results into the synthesis prompt as structured items: claim, source URL, page, publication date.

      Tempting distractorAssume the synthesis agent can read the coordinator's history, or give it the web-search tool so it can find the sources again.

    6. Fewer, scoped tools per agent.4–5 role-specific tools beat 18. Agents misuse tools outside their specialty.

      ExampleOne agent holds 18 tools. During writing, the synthesis step keeps launching fresh web searches and drifting off-topic.

      Right fixSplit into specialists. Search gets the search tools; synthesis gets only writing tools plus a narrow verify_fact for quick checks.

      Tempting distractorKeep all 18 tools on one agent and make every description longer.

    7. Errors must be structured and honest.Category, retryable flag, what was attempted, partial results. Never “operation failed,” never empty-results-as-success, never crash the workflow on one failure. An empty result is not an error.

      ExampleThe order database times out, lookup_order returns [], and the agent tells the customer they have no orders.

      Right fixReturn {"isError": true, "errorCategory": "transient", "isRetryable": true, "message": "Order DB timed out after 5s"}. The agent retries or tells the customer it is checking, instead of claiming there are no orders.

      Tempting distractorReturn "Operation failed" for every problem, or keep returning an empty list so the conversation does not break.

    8. Loops stop on stop_reason, not text.Continue on "tool_use", stop on "end_turn". Iteration caps are a safety net, not the stopping mechanism.

      ExampleThe loop ends when the reply contains “done”. Claude writes “Done checking the order, now let me look up the refund policy” and the loop stops halfway.

      Right fixKeep looping while stop_reason == "tool_use" and stop on "end_turn". Keep a cap of around 25 iterations only as a guard against runaway loops.

      Tempting distractorLook for a stricter phrase like “TASK COMPLETE”, or stop after a fixed 10 iterations.

    9. Independent eyes review better.A fresh instance without the generator's reasoning catches more than self-review. Big reviews use per-file passes plus one cross-file pass.

      ExampleIn CI, the session that wrote a feature also reviews it and approves a null-pointer bug. On a 20-file PR, the review is deep on the first files and shallow on the rest.

      Right fixRun the review in a separate session with no generator context. Review each file on its own, then do one cross-file pass for data flow between files.

      Tempting distractorAsk the same session to “review your work again carefully”, or review all 20 files in one pass with a larger context window.

    10. Protect what matters in context.Facts (amounts, dates, IDs) go in a persistent case-facts block. Trim tool output. Put the key summary first (lost in the middle). Keep claim-to-source mappings and dates through synthesis.

      ExampleForty turns into a support chat, the running summary has turned “$1,247.50 refund on order 88213, promised by Friday” into “customer wants a refund.”

      Right fixKeep a case-facts block (order 88213, $1,247.50, due Friday, status pending) attached to every prompt, outside the summarized history. Trim each order lookup to the five fields that matter.

      Tempting distractorSwitch to a model with a larger context window, or summarize the history more often.

    Two more reflexes

    Two bonus rules that answer many Domain 4 questions. You'll meet them again in that module.

    1. Explicit criteria beat vague instructions.Telling Claude how careful to be doesn't change its behavior reliably. Telling it exactly what counts does. Name the categories to report and the ones to skip, and define severity with concrete examples.

      ExampleA CI review bot flags so many false positives that developers start ignoring every comment, including real bugs. The prompt says “Be conservative and only report high-confidence issues.”

      Right fix“Report only bugs that cause wrong results, security holes, and comments that contradict the code. Skip style, naming and formatting.” If one category is still noisy, turn it off temporarily to win back trust.

      Tempting distractor“Only report issues you are 95% sure about,” or add “be conservative” at both the start and end of the prompt.

      Task 4.1

    2. Match the API to latency.The Message Batches API costs about 50% less but can take up to 24 hours, with no speed guarantee and no multi-turn tool use inside a request. Use it only when nobody is waiting for the answer.
      Use batchKeep real-time
      Overnight reports, weekly auditsPre-merge PR checks (a developer is waiting)
      Nightly test generationLive customer support (a customer is waiting)
      Backfilling 10,000 documentsAny agent that loops through tools

      ExampleTo cut costs, a manager wants to move both the pre-merge PR checks and the nightly tech-debt report to the Batch API.

      Right fixBatch only the nightly report. Pre-merge checks block a developer, so they stay real-time. If a batch job has a 30-hour SLA, submit at least every 6 hours (6 h wait + 24 h processing).

      Tempting distractor“Batch both, since 50% savings outweighs latency,” or “batch the pre-merge checks because they run more often.”

      Task 4.5

    The one-line version. Say exactly what you want, not how hard to try; and only batch the work nobody is waiting on.

    Domain 1: Agentic Architecture & Orchestration

    How autonomous agents loop, delegate, enforce rules and keep state. This is the biggest domain, so give it a full hour.

    1.1

    Agentic loops

    while True:
    resp = client.messages.create(model=..., tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":   # "end_turn" -> done
        break
    results = [run(b) for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})  # tool_result blocks
    Concept
    An agent is a loop around the Messages API: send messages and tools, read stop_reason. If it is "tool_use", run the requested tools, append tool_result blocks (matching each tool_use_id) as a user turn, and call again. If it is "end_turn", the task is done. Claude decides which tool comes next, unlike a hard-coded decision tree.
    Exam answer
    Continue on tool_use, terminate on end_turn, and always append tool results so the model reasons on them.
    Trap
    Parsing the assistant text for “done”; a max-iteration cap as the primary stop; forgetting to append tool results, so the model re-calls the tool. Also know max_tokens (output was cut off; raise the limit or continue, it is not done), stop_sequence, pause_turn, refusal.
    1.2

    Coordinator and subagents (hub-and-spoke)

    Concept
    A coordinator decomposes the task, picks which subagents to invoke, aggregates results and handles errors. Subagents never talk to each other directly; everything routes through the hub for observability and consistent error handling.
    Exam answer
    The coordinator chooses subagents by query complexity rather than running the full pipeline every time, partitions scope to avoid duplicate work, and runs a refinement loop: evaluate the synthesis, find gaps, re-delegate.
    Trap
    Blaming subagents when coverage is incomplete. If every subagent did its assigned job and the report still misses whole areas (“creative industries” covered only visual arts), the coordinator decomposed too narrowly.
    1.3

    Spawning subagents and passing context

    Concept
    In the Agent SDK, subagents are spawned via the Task tool, so the coordinator's allowedTools must include "Task". Each subagent type is an AgentDefinition: description, system prompt, restricted tools. Subagents do not inherit the parent's history or memory.
    Exam answer
    Put complete prior findings in the subagent's prompt. Use structured formats that separate content from metadata (URL, page, date) so attribution survives. Spawn in parallel by emitting multiple Task calls in one coordinator response. Give the coordinator goals and quality criteria, not a step-by-step script.
    Trap
    Assuming the synthesis subagent can see what search found; spawning one subagent per turn when they could run in parallel; micromanaging the coordinator. fork_session branches from a shared baseline to explore alternatives.
    1.4

    Multi-step workflows: enforcement and handoff

    Concept
    Some step orders are business-critical, such as verifying identity before refunding. Prompt guidance has a non-zero failure rate; programmatic prerequisites do not.
    Exam answer
    A programmatic gate blocks lookup_order and process_refund until get_customer returns a verified ID. Multi-concern requests: split into distinct items, investigate in parallel, return one unified resolution. Escalation: hand the human a structured summary (customer ID, issue, root cause found, actions tried, recommended next step).
    Trap
    “Strengthen the system prompt” or “add few-shot examples” for an ordering rule that fails 12% of the time; a routing classifier, which controls which tools exist, not their order.
    1.5

    Agent SDK hooks

    Concept
    Hooks run your code at fixed points in the loop. PreToolUse intercepts an outgoing call to allow, block, modify or redirect it. PostToolUse intercepts a tool's result before Claude sees it.
    Exam answer
    PostToolUse normalizes messy data from different MCP tools (Unix timestamps vs ISO 8601, numeric status codes to labels, trimming fields). Pre-call interception blocks policy violations, such as a refund over $500, and redirects to escalate_to_human. Choose hooks whenever compliance must be guaranteed.
    Trap
    Asking the model to “remember the refund limit” or to convert formats itself.
    1.6

    Task decomposition

    Concept
    This is how a coordinator chooses its breakdown (see the FAQ on coordinator decomposition). Prompt chaining is a fixed sequence of steps, good when the steps are known in advance. Adaptive decomposition generates subtasks from what each step discovers, good for open-ended investigation.
    Exam answer
    Predictable multi-aspect review uses chaining, for example per-file analysis followed by a cross-file integration pass. Open-ended work (“why is checkout slow?”) maps the structure first, finds high-impact areas, and builds a prioritized plan that adapts.
    Trap
    One giant prompt for a 14-file review (attention dilution); a rigid pipeline for an investigation whose next step depends on what it finds.
    1.7

    Session state: resume, fork, fresh start

    Concept
    --resume <session-name> continues a named session. fork_session creates independent branches from one shared baseline. A fresh session with an injected structured summary avoids stale context.
    Exam answer
    Resume when prior context is mostly valid, and tell the agent which files changed so it re-analyzes just those. Fork to compare two approaches from the same baseline. Start fresh with a summary when old tool results are stale.
    Trap
    Resuming a session whose tool results describe code that has since changed, without telling the agent; redoing the whole analysis to compare two approaches instead of forking.

    X1

    Claude Code architecture, permissions and settings

    Key idea: nothing destructive runs silently. Claude only acts through tool calls, and every call passes a permission check first. What the exam keeps testing is which actions run on their own and which need your approval.
    Action (default mode)Needs approval?How to change it
    Read-only tools: Read, Grep, GlobNo, runs automaticallyBlock specific files with a deny rule
    File edits: Edit, WriteYesacceptEdits mode, or an allow rule
    Shell commands: BashYesallow rules for safe commands, e.g. Bash(npm test)
    Web fetches and MCP toolsYesallow rules per tool
    Anything matching a deny ruleBlocked, never runsRemove the rule (deny is checked first and wins)

    Rules are checked in the order deny → ask → allow, so a deny rule beats an allow rule for the same action. A PreToolUse hook adds one more gate on top that you control with code (card X5).

{
  "permissions": {
    "allow": ["Bash(npm test)", "Bash(npm run lint)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Read(./secrets/**)"]
  }
}
    Settings fileScopeShared?
    Managed (enterprise) settingsWhole organization; can’t be overriddenSet by IT
    ~/.claude/settings.jsonAll your projectsNo
    .claude/settings.jsonThis projectYes, committed to git
    .claude/settings.local.jsonThis project, just youNo, git-ignored

    Precedence when settings conflict: managed > command-line flags > settings.local.json > project settings.json > user settings.json. Permission modes: default (ask), acceptEdits, plan (read-only exploration), bypassPermissions.

    Concept
    Claude Code acts only through explicit tool calls (Read, Write, Edit, Bash, Grep, Glob, MCP tools). Claude proposes an action; the permission system decides whether it runs automatically, asks you first, or is blocked. Context lasts within a session. A new session starts blank and is re-established from CLAUDE.md, so anything that must survive between sessions belongs there, not in the chat.
    Exam answer
    Auto-approve safe, repeated commands (npm test) and deny reads of secrets (.env) with permission rules. Team rules go in .claude/settings.json; personal tweaks for one project go in .claude/settings.local.json. A convention Claude must follow every session goes in the project CLAUDE.md.
    Trap
    Expecting a new session to remember yesterday’s chat; telling Claude in the prompt “don’t read .env” (probabilistic) instead of a deny rule; using bypassPermissions or --dangerously-skip-permissions outside a sandbox.
    X2

    CLAUDE.md layering and keeping files out of context

    Exam fact: one scope model everywhere. Every kind of Claude Code configuration follows the same two tiers: a project file in the repo that the team shares through git, and a user file in your home folder that only you get. If you know which tier a question needs, you know the file.
    WhatProject: shared via gitUser: personal / experimental
    Instructions./CLAUDE.md or .claude/CLAUDE.md~/.claude/CLAUDE.md
    MCP servers.mcp.json at the repo root~/.claude.json
    Settings, permissions, hooks.claude/settings.json~/.claude/settings.json (or .claude/settings.local.json for one project)
    Commands and skills.claude/commands/, .claude/skills/~/.claude/commands/, ~/.claude/skills/
    Subagents.claude/agents/~/.claude/agents/

    Note the odd one out: MCP’s user file is ~/.claude.json (a file in your home folder), not inside ~/.claude/. “Override or extend” on the slide means the same thing as “most specific wins”: a subdirectory file or path rule can add to the parent’s instructions, and where they conflict, the narrower one applies. Above both tiers sits the enterprise level, which IT manages and nobody can override.

    About .claudeignore. It isn’t mentioned in Claude Code’s official docs, but exam questions sometimes ask about it. To keep files out of Claude’s context you can use either: a deny rule in settings, such as Read(./.env) (the documented way), or a .claudeignore file, which exam prep material describes as working like .gitignore. If either appears as the option for excluding files from context, it’s the right idea.
    Concept
    CLAUDE.md files stack in layers: enterprise (managed policy file set by IT) → user (~/.claude/CLAUDE.md) → project (./CLAUDE.md) → subdirectory. All of them load; when instructions conflict, the most specific wins. Subdirectory files load when Claude works in that folder, and .claude/rules/ files with paths load only for matching files (Task 3.3).
    Exam answer
    Organization-wide rules (security, compliance) go in the enterprise file; team standards in project CLAUDE.md; folder-specific conventions in a subdirectory CLAUDE.md or a path rule. To keep files such as secrets or huge generated folders away from Claude, use deny rules like Read(./secrets/**) in settings.
    Trap
    Putting org-wide rules in one developer’s user file; assuming only the nearest CLAUDE.md loads (they all load, specific ones win on conflict). For MCP, mixing up .mcp.json (project, shared) and ~/.claude.json (user, personal) is a classic distractor.
    X3

    Skill frontmatter beyond the basics

    Term to know: progressive disclosure. A skill loads in stages, so you pay context only for what’s used. The short description sits in context from the start (cheap). The full SKILL.md body loads only when the skill is triggered. Bundled files load only if the instructions call for them. This keeps the base context window lean, unlike CLAUDE.md, which loads in full every session.
    StageWhat loadsWhenContext cost
    1. Metadataname + descriptionAlways, at session startA line or two per skill
    2. InstructionsThe SKILL.md bodyOnly when the skill is triggeredThe full procedure
    3. ResourcesBundled files: reference docs, templates, scriptsOnly if the instructions need them; scripts can run without their code entering contextOnly what’s used

    Exam angles: (1) “Why move a 12-step procedure out of CLAUDE.md into a skill?” Progressive disclosure: only its description costs context until it’s needed. (2) “The skill never triggers”: Claude decides from stage 1 alone, so fix the description. (3) With disable-model-invocation: true, even the description stays out of context, because Claude never needs to decide whether to use it.

    Common exam traps

    The first four come from your slide deck; the last four come up repeatedly elsewhere in this course.

    Trap 1Assuming a subdirectory CLAUDE.md is merged or averaged with the parent.

    Why it’s wrongThe more specific scope wins. Where a subdirectory rule conflicts with a parent rule, the subdirectory rule applies outright; the two are never blended into a compromise. Parent rules that don’t conflict still apply, because every layer is loaded.

    ExampleRoot says “2-space indent”, legacy/CLAUDE.md says “4-space indent”: files in legacy/ get 4 spaces, not 3.

    Trap 2Confusing .mcp.json (project, shared) with ~/.claude.json (user, personal).

    Why it’s wrongProject config is version-controlled and team-shared; user config is local and experimental. Decide which one the question describes first.

    Example“Everyone who clones” → .mcp.json. “Try a server without affecting teammates” → ~/.claude.json.

    Trap 3Choosing direct execution for a large, high-risk, exploratory change.

    Why it’s wrongPlan mode is the safer, exam-correct choice whenever the blast radius or ambiguity is high.

    Example“Migrate 45 files to a new auth library” → plan mode. “Fix a typo in one file” → direct.

    Trap 4Using a hook where model judgment is needed, or vice versa.

    Why it’s wrongHooks give deterministic guarantees: use them for hard constraints you can write as an if. Nuanced decisions belong to the model, guided by the prompt.

    Example“Never run rm -rf” → hook. “Escalate when policy is ambiguous” → prompt criteria with few-shot examples.

    Trap 5Expecting exit code 1 to block a hook’s action.

    Why it’s wrongOnly exit code 2 blocks. Exit 1, like any other non-zero code, is a non-blocking warning and the action proceeds.

    ExampleA safety-net hook that “fails” with exit 1 lets the dangerous command run.

    Trap 6Putting team standards in a user-level file.

    Why it’s wrong~/.claude/ files reach only their owner. Anything the team relies on goes in the repo’s .claude/ or root CLAUDE.md.

    Example“Works for the senior dev, not the new hire” is the classic symptom.

    Trap 7Running Claude Code in CI without -p.

    Why it’s wrongThere’s no TTY in CI, so any prompt waits forever.

    Example“The pipeline hangs until it times out” → -p.

    Trap 8Committing secrets in .mcp.json.

    Why it’s wrongReference them as environment variables with ${VAR} expansion.

    Example"Authorization": "Bearer ${GITHUB_TOKEN}".

    Domain 4: Prompt Engineering & Structured Output

    How to get precise, parseable, trustworthy output at production scale. This is prompting for pipelines, not chat.

    4.1

    Explicit criteria

    Concept
    Vague instructions (“be conservative,” “only high-confidence issues”) do not change behavior reliably. Specific categorical criteria do.
    Exam answer
    State exactly what to report (bugs, security, comments that contradict the code) and what to skip (style nits, local conventions). Define each severity level with a concrete code example. If one category produces many false positives, temporarily disable it to restore trust while you fix it.
    Trap
    “Tell it to be more careful”; “only report findings above 90% confidence.”
    4.2

    Few-shot examples

    Concept
    Few-shot is the most effective way to get consistent format and to show how ambiguous cases should be handled. Good examples generalize to cases you did not list.
    Exam answer
    2–4 targeted examples of the ambiguous cases, each showing the reasoning for the chosen action and the exact output format. For extraction, show varied document layouts and informal values; this reduces hallucination and empty fields.
    Trap
    Dozens of easy examples; happy-path-only examples.
    4.3

    Structured output with tool use and JSON schema

    Concept
    Define a tool whose input_schema is your output schema; the tool_use block's input is your JSON. A schema removes syntax errors (malformed JSON, missing keys). It does not prevent semantic errors: totals that do not add up, a value in the wrong field, a plausible invented value.
    Exam answer
    Make fields that may be absent nullable, since required fields push the model to invent. Give enums an "other" value plus a detail string, and "unclear" for ambiguous sources. Put normalization rules (ISO dates, numeric currency) in the prompt. Use tool_choice: "any" when several schemas exist; force a named tool to run it first.
    Trap
    “Ask for JSON in the prompt and parse it”; making every field required “for completeness.”
    4.4

    Validation, retry and feedback

    Concept
    Retry-with-error-feedback: send the original document, the failed extraction and the specific errors (“line items sum to 410, total says 450”).
    Exam answer
    Add self-check fields such as calculated_total beside stated_total and conflict_detected. Add detected_pattern to findings so you can analyze which patterns get dismissed. Retries help with format and structure; they do not help when the information is missing from the source. Return null and route to review.
    Trap
    Blind retries with the same prompt; retrying until a value appears.
    4.5

    Message Batches API

    Concept
    About 50% cheaper, up to 24 hours to complete, no latency SLA, no multi-turn tool calling inside a request, and custom_id to match requests to results.
    Exam answer
    Batch overnight reports, weekly audits, nightly test generation and backfills. Keep anything blocking (pre-merge checks, live support) synchronous. SLA math: with a 30-hour SLA and up to 24 hours of processing, submit at least every 6 hours. On partial failure, resubmit only the failed custom_ids with fixes. Tune the prompt on a sample first.
    Trap
    Moving pre-merge checks to batch to save 50%; resubmitting the whole batch.
    4.6

    Independent and multi-pass review

    Concept
    The instance that wrote something keeps its reasoning in context and tends to agree with itself.
    Exam answer
    Use a second, independent instance without the generator's context. Split big PR reviews into per-file passes plus one cross-file integration pass. Ask for a confidence value per finding in a verification pass.
    Trap
    “Ask the same session to double-check its work”; one pass over 14 files with a bigger context window.

    "type": "object",
    "properties": {
      "order_id": {

      "amount": {
        "type": "number",

        "maximum": 500,
        "description": "Refund amount in USD"
      },
      "reason": {
        "type": "string",

      },
      "reason_detail": {
        "type": "string",
        "maxLength": 200,

      },
      "notify_customer": {

      }

    Concept

    Free-text categories become an enum (plus "other" and a detail field); amounts become numbers with minimum/maximum; IDs get a pattern; dates say their format; optional fields say what happens when they’re left out.
    Trap
    Everything typed as a free-text string; every field required (Claude is pushed to invent values, the same lesson as extraction schemas in Task 4.3); an optional field with no stated default, so nobody knows what happens when it’s omitted.

    Y3

    Tool error handling: categories, idempotency, partial success

    Decision rule: retry only what can succeed next time. Transient errors (a timeout, a 503) trigger an automatic retry with backoff. Business errors (“item out of stock”) and permission errors (“not authorized”) are not retried: surface them to the user or escalate.

    Backoff means waiting longer between each attempt, for example 1 s, then 2 s, then 4 s, with a maximum number of tries, so a struggling service isn’t hammered. Pair it with an idempotency key so the retries are safe.

    Idempotency: why a retry can double-refund

    1. Claude calls process_refund for $120.
    2. The payment system completes the refund, but the response times out.
    3. Claude sees a transient error and retries.
    4. Without idempotency: a second $120 refund. With an idempotency_key: the server recognises the repeat and returns the original result.
    { "order_id": "ORD-048812", "amount": 120.00, "reason": "damaged",
  "idempotency_key": "refund-ORD-048812-2026-11-20-001" }

    Partial success: report both halves

    {
  "processed": [ { "order_id": "ORD-000101", "refund_id": "R-9001" },
                 { "order_id": "ORD-000102", "refund_id": "R-9002" } ],
  "failed":    [ { "order_id": "ORD-000103", "errorCategory": "business",
                   "isRetryable": false,
                   "message": "Refund exceeds the $500 limit; needs human approval" } ]
}

    The agent can confirm the two refunds that worked and escalate only the third, rather than redoing everything or telling the customer nothing happened.

    Concept
    Structured errors tell the agent what kind of failure happened so it can choose the right recovery (Task 2.2). Two more ideas matter for production tools. Idempotency: calling the tool again with the same input must be safe, with no duplicate side effects. Partial success: when a call handles several items, return what succeeded alongside what failed, instead of all-or-nothing.
    Exam answer
    Error responses carry a category, a retryable flag and a clear message. Write tools that create or change things accept an idempotency key so a retry after a timeout can’t double-apply. Batch tools return processed and failed lists, each failure with its own category.
    Trap
    Retrying a non-idempotent write after a timeout (the first call may have succeeded, so the customer is refunded twice); failing a 10-item batch because 1 item failed; a generic “Operation failed.”

    Key idea: choose the transport by who shares the server. stdio is simplest for local, single-user, trusted integrations, such as tools on a developer’s own machine.     Concept
    The Model Context Protocol (MCP) is an open standard for connecting models to external tools and data: one protocol, many servers. The host (Claude Code, the Claude app, or your agent) runs an MCP client for each server it connects to. Servers expose three primitives and connect over a transport.
    Exam answer
    Choose the primitive by who starts it: the model (tool), the application (resource) or the user (prompt). Use stdio for a local tool on the developer’s machine and a remote transport (HTTP) for a shared service. For standard systems such as GitHub, use an existing community server rather than building your own.
    Trap
    Exposing a read-only catalog (a database schema, a docs tree) as dozens of tools instead of a resource; building a custom server for a system that already has one; assuming a remote server must use stdio.
    2.4

    MCP servers in Claude Code and agents

    Concept

    Exam answer
    Shared servers go in .mcp.json with environment variable expansion (Bearer ${GITHUB_TOKEN}) so no secret is committed. All servers' tools are discovered at connect time and available together. Prefer a community server over a custom one for standard integrations.
    Trap
    Hard-coded tokens in .mcp.json; team servers in ~/.claude.json; building a custom GitHub server.

    Common exam traps

    The first four come from your slide deck; the rest come up repeatedly elsewhere in this domain.

    Trap 1Retrying a business error (e.g. “insufficient inventory”) automatically, like a timeout.

    Why it’s wrongOnly transient errors should auto-retry, with backoff. Business and permission errors need surfacing or escalation, not repetition.

    ExampleFive retries of “out of stock” just produce five identical failures.

    Trap 2Two tools with near-identical descriptions offered as an acceptable design.

    Why it’s wrongOverlapping descriptions cause wrong-tool routing. Descriptions must clearly differentiate purpose and scope.

    Exampleanalyze_content and analyze_document, both “Analyzes text.”

    Trap 3Using a single broad credential shared across many tools “for simplicity.”

    Why it’s wrongLeast privilege means scoping credentials and permissions per tool or integration, not sharing one broad grant.

    ExampleA read-only review agent holding the same admin GitHub token as the deploy tool.

    Trap 4Choosing SSE for a simple, single-user, local dev integration.

    Why it’s wrongstdio is the simpler, correct choice for local single-user cases; keep remote transports (SSE, or HTTP in current docs) for shared or remote deployments.

    ExampleA server that reads files on your own laptop → stdio.

    Trap 5Fixing wrong-tool selection with few-shot examples or a router.

    Why it’s wrongDescriptions are the routing signal. Rewrite them: what, when (and when not), what it returns.

    Example“Agent calls get_customer for order questions” → improve both descriptions.

    Trap 6Accepting free text and validating afterwards.

    Why it’s wrongConstrain inputs in the schema: enums, patterns, min/max, formats.

    Example"reason": {"type": "string"} → an enum with "other".

    Trap 7Making every parameter required.

    Why it’s wrongRequired fields push Claude to invent values. Require only what the tool can’t work without, and state defaults for the rest.

    ExampleOptional limit → “defaults to 20.”

    Trap 8Retrying a write that isn’t idempotent.

    Why it’s wrongA timeout doesn’t mean the action failed. Use an idempotency key so repeats are safe.

    ExampleA retried refund pays the customer twice.

    Trap 9Returning all-or-nothing results for batch tools.

    Why it’s wrongReport what succeeded and what failed, each failure with its category.

    Example9 of 10 refunds worked; escalate just the tenth.

    Trap 10Trusting the model to respect a security boundary.

    Why it’s wrongScope credentials and validate on the server; the model’s choices can be manipulated.

    Example“Never delete” in the prompt, but the token can delete.

    Trap 11Exposing a read-only catalog as many tools.

    Why it’s wrongUse an MCP resource so the agent can see what exists without exploratory calls.

    ExampleA database schema browsed via 30 describe_table calls.

    Domain 5: Context Management & Reliability

    The lightest domain by weight, but its ideas appear in every scenario: keeping the right information in context, handing off to humans, and staying honest about uncertainty.

    5.1

    Preserving information in long interactions

    Concept
    Three failure modes. Progressive summarization blurs exact facts (“$1,247.50 refund on order 88213 by Friday” becomes “wants a refund”). Lost in the middle: models attend best to the start and end of long input. Verbose tool results (40 fields when 5 matter) crowd out what matters.
    Exam answer
    Keep a persistent case-facts block (amounts, dates, IDs, statuses, promises) in every prompt, outside summarized history. Trim tool output before it accumulates (a PostToolUse hook does this well). Put the key-findings summary at the top with clear section headers. Have upstream agents return structured data instead of prose. Send full history on each call; the API is stateless.
    Trap
    “Use a bigger context window”; summarizing more aggressively.
    5.2

    Escalation and ambiguity

    SituationRight move
    Customer explicitly asks for a humanEscalate immediately; do not investigate first
    Frustrated, but the issue is simple and in scopeAcknowledge, offer to resolve; escalate if they ask again
    Policy silent or ambiguous (competitor price match)Escalate; it is a policy gap
    No progress after reasonable attemptsEscalate with a structured handoff
    Tool returns several matching customersAsk for another identifier; never pick by heuristic
    Concept
    Escalation triggers are an explicit request for a human, a policy gap, or no meaningful progress. Sentiment and self-reported confidence are not.
    Exam answer
    Put explicit escalation criteria with few-shot examples (escalate vs resolve) in the system prompt.
    Trap
    Sentiment-based escalation (anger is not complexity); self-reported confidence (poorly calibrated on exactly the hard cases); a separate ML classifier.
    5.3

    Error propagation across agents

    Concept
    The coordinator can only recover well if it knows what failed and what is still usable.
    Exam answer
    The subagent returns structured context: failure type, the query attempted, partial results, possible alternatives. It retries transient failures locally first. Access failures are reported differently from valid empty results. Final reports carry coverage annotations showing which conclusions are well supported and where sources were missing.
    Trap
    A generic “search unavailable”; swallowing the error and returning empty results; letting one exception kill the job.
    5.4

    Context in large codebase exploration

    Concept
    In long sessions answers drift: Claude cites “typical patterns” instead of the specific classes it found earlier. That is context degradation.
    Exam answer
    Delegate specific questions to subagents (“find all test files,” “trace refund flow dependencies”). Keep a scratchpad file of key findings. Summarize each phase before spawning the next. For crash recovery, each agent writes state to a known location and the coordinator loads a manifest on resume. Use /compact when discovery output fills the context.
    Trap
    Restarting from scratch every time; one agent reading the whole repository.
    5.5

    Human review and confidence calibration

    Concept
    “97% accurate overall” can hide 70% accuracy on one document type or one field.
    Exam answer
    Measure accuracy by document type and by field before reducing review. Use stratified random sampling of high-confidence outputs to keep measuring errors and catch new patterns. Have the model emit field-level confidence, then calibrate thresholds on a labeled validation set. Route low-confidence or contradictory items to people first.
    Trap
    Trusting raw model confidence; auto-approving everything because the aggregate number looks good.
    5.6

    Provenance and uncertainty in synthesis

    Concept
    Attribution gets lost when findings are compressed without their sources.
    Exam answer
    Subagents output claim-to-source mappings (URL, document, excerpt) that synthesis preserves. When credible sources conflict, report both with attribution. Require publication or collection dates so a 2021 figure and a 2025 figure are not read as a contradiction. Separate settled from contested findings, and render each content type naturally (tables for financials, prose for news).
    Trap
    Averaging conflicting numbers; dropping citations while summarizing; forcing everything into one format.

    What does “coordinator decomposition” mean?

    Coordinator decomposition is how the lead agent splits a big task into smaller subtasks and hands each one to a helper agent.

    A multi-agent system has two roles:

    • The coordinator is the manager. It receives the request, decides which pieces of work are needed, and assigns each piece to a subagent.
    • The subagents are the workers. Each does only the piece it was given. They don't see the original request or each other's work.

    “Decomposition” just means “breaking down.” So coordinator decomposition is the coordinator's plan: which subtasks exist and what each one covers.

    An everyday analogy

    You ask a manager for a report on “how remote work affects companies.” The manager assigns three people:

    1. Research productivity studies.
    2. Research employee satisfaction surveys.
    3. Research collaboration tools.

    All three do excellent work. But the report says nothing about office real estate, hiring across cities, or tax and legal issues. Nobody did their job badly. The manager's breakdown left those areas out. That is a coordinator decomposition failure.

    How it shows up on the exam

    “The research report on creative industries covers only visual arts and misses music, film and writing. Logs show every subagent completed its task correctly. What is the root cause?”

    The wrong options blame a worker: the search agent's queries were too narrow, the synthesis agent dropped findings, or the context window was too small. The phrase “every subagent completed its task correctly” is your signal. If the workers did their jobs and coverage is still incomplete, the gaps were never assigned. The answer is that the coordinator's decomposition was too narrow.

    What good decomposition looks like

    • Covers the whole topic. Together, the subtasks span everything the question asks.
    • Doesn't overlap. Two subagents don't research the same thing twice.
    • Fits the question. A simple factual question may need one subagent, not all five.
    • Checks its own coverage. When results come back, the coordinator looks for gaps and sends out more subtasks if something is missing.
    RememberWorkers did their job but something is missing? Blame the manager's plan.

    What is a routing classifier?

    A routing classifier is a separate component that sits in front of Claude and decides where a request should go before Claude ever sees it. It reads the user's message, labels it (“billing question,” “order question”), and sends it to a particular tool, agent or workflow based on that label.

    A concrete picture

    • Without a router: the customer types “Where's my order #48812?” Claude reads the message and the tool descriptions, then picks lookup_order itself.
    • With a router: the message first hits a small model or rules engine trained on labeled examples. It outputs a label like ORDER_INQUIRY. Your code then calls lookup_order directly, or gives Claude only the order-related tools for that turn.

    Think of a receptionist who hears why you called and transfers you to the right department, so the department never has to work out whether you're in the right place.

    Why it's usually the wrong answer on the exam

    It appears as a distractor in two kinds of questions.

    1. Wrong tool picked. The agent confuses get_customer and lookup_order, which both have one-line descriptions. A router would technically help, but it's a new component to train, label data for, deploy and maintain, and it works around the real problem. The root cause is vague tool descriptions; the fix is rewriting them. That's Rule 3: proportionate beats elaborate.
    2. Steps done in the wrong order. The agent sometimes calls process_refund before verifying the customer. A router decides which tools or agents handle a request. It doesn't control what order things happen in. The fix is a programmatic gate or hook that blocks the refund until identity is verified. That's Rule 1: must-always rules go in code.

    A close cousin to watch for

    “Train a separate classifier to decide escalations” is the same trap in Domain 5. The right answer there is explicit escalation criteria with few-shot examples in the system prompt.

    RememberA routing classifier is an extra gatekeeper model that picks the path for each request. On this exam it's almost always the over-engineered option; look for the simpler fix that addresses the cause.

    Can the synthesis agent read the coordinator's history?

    No. That idea is a trap, not a fact. A subagent sees only what the coordinator puts in the prompt it sends. Nothing else carries over.

    The setup

    • The coordinator talks to the user, plans the work, and spawns helpers.
    • The search subagent goes out and finds sources.
    • The synthesis subagent writes the final report.

    It's natural to picture them as one team sharing a whiteboard: the coordinator saw everything, so the writer can surely look back at it. That's the wrong mental model.

    What actually happens

    When the coordinator spawns a subagent with the Task tool, the subagent starts with a brand-new, empty conversation. It has its own system prompt (from its AgentDefinition), its own tools, and only the text the coordinator puts in the prompt.

    It does not see the user's original message, the coordinator's planning, what the search subagent found, or any shared memory. Each subagent is like a contractor you email a brief to: they know what's in the email and nothing else. That's Rule 5: subagents start blank.

    How the bug shows up

    The search subagent finds 12 good sources. The coordinator spawns the synthesis subagent with “Write the final report on renewable energy adoption.” The report comes back generic, with no citations, as if the research never happened. From the synthesis agent's point of view, it didn't: nobody handed it the findings.

    The right fix

    The coordinator passes the findings into the synthesis prompt explicitly, ideally as structured data. Keeping claim, source, page and date together keeps citations attached as content moves between agents.

    Write the report using ONLY these findings:
[
  {"claim": "Solar capacity grew 24% in 2025",
   "source": "https://...", "page": 12, "published": "2026-02"},
  ...
]

    Distractors you'll see

    DistractorWhy it's wrong
    “Enable shared memory so subagents read the coordinator's history”No such setting; subagents are isolated by design
    “Give the synthesis agent the web-search tool”Duplicates the search agent's job and invites misuse of tools outside its role (Rule 6)
    “Increase the synthesis agent's max_tokens”Output length isn't the problem; the input never arrived
    “Tell the synthesis agent to use all available findings”It has no findings available to use
    RememberSubagents only know what's in the prompt you send them. If the report is missing what another agent found, the coordinator never passed it along.

    How does stop_reason work?

    stop_reason is a field on every Messages API response that tells you why Claude stopped generating this time. Your agent loop reads it to decide what to do next. The text is for humans; stop_reason is for your code.

    {
  "role": "assistant",
  "content": [ ...text and/or tool_use blocks... ],
  "stop_reason": "tool_use"
}

    Where it comes from

    stop_reason is generated by Anthropic's API, on the server side, as part of each response. Your code never sets it; it only reads it. Claude generates the response token by token, and when generation ends, the API records why.

    • Claude's own decision: "end_turn" when it has finished its answer; "tool_use" when it writes a tool_use block and can't continue until your code runs the tool.
    • Triggered by your request settings: "max_tokens" when the response hits the max_tokens limit you set; "stop_sequence" when Claude produces one of the stop_sequences you passed in.
    Your code                     Anthropic API              Claude model
---------                     -------------              ------------
messages.create(...)  ──────►  runs the model  ────────►  generates tokens...
                                                          stops (done, wants a tool,
                                                          hit a limit, etc.)
                               labels WHY it stopped ◄──
response + stop_reason ◄──────
reads stop_reason,
decides what to do next

    Because the API sets it from what actually happened, it's a reliable machine signal. The text Claude writes is just words; it might say “done” while still needing a tool. That's why you trust stop_reason over the text.

    The two values that run the agent loop

    ValueWhat it meansWhat your loop does
    "tool_use"Claude wants a tool run before it can continueRun the tool(s), send the results back, call the API again
    "end_turn"Claude is finished with its answerStop looping and return the answer
    1. Call the API with the messages and tools.
    2. Read stop_reason.
    3. If it's "tool_use": run each requested tool and append a tool_result with the matching tool_use_id as the next user message. Go back to step 1.
    4. If it's "end_turn": you're done.

    A walk-through

    A customer asks “Can I return order #48812?”

    CallClaude responds withstop_reasonYour code
    1lookup_order(order_id="48812")"tool_use"Runs the lookup: delivered 10 days ago
    2get_return_policy()"tool_use"Runs it: 30-day window
    3“Yes, you're within the 30-day window…”"end_turn"Exits the loop

    Claude chose how many tools to call and in what order. Your code never guessed; it followed stop_reason.

    Other values to recognize

    ValueWhat it meansRight reaction
    "max_tokens"Output hit your max_tokens limit mid-answerIt's truncated, not finished. Raise the limit or continue the generation.
    "stop_sequence"Claude produced one of your custom stop stringsHandle it the way you designed that stop string
    "pause_turn"A long-running server-side step paused the turnSend the conversation back to let it continue
    "refusal"Claude declined to continueDon't retry blindly; handle it as a refusal

    Who acts on it

    Your code, not the end user. The customer never sees stop_reason. Your agent loop checks it after every API call and acts automatically: return a complete answer, run tools and loop, or handle a cut-off response by raising the limit.

    "tool_use" isn't “incomplete” in a bad sense. It's the normal middle of an agent's work: a typical task goes tool_use → tool_use → end_turn. Only "max_tokens" means something went wrong with the output. Most loops come down to three branches:

    if stop_reason == "tool_use":
    # run tools, append tool_result blocks, call the API again
elif stop_reason == "max_tokens":
    # truncated: raise the limit or continue the generation
else:
    # "end_turn" (or another final state): done, return the answer

    What the exam tests

    Rule 8: loops stop on stop_reason, not text. The wrong answers decide “are we done?” some other way:

    • Reading the text. “Stop when the reply says ‘done’ or ‘TASK COMPLETE’.” Claude might write “Done checking the order, now let me look up the policy,” and the loop quits halfway.
    • Iteration caps as the main stop. “Stop after 10 loops.” Some tasks need 12 steps, some need 2. A cap is a safety net against runaway loops, not how you know the task is finished.
    • Treating max_tokens as finished. The answer was cut off, so passing it on gives the user half a response.
    Debugging pattern. If Claude keeps requesting the same tool over and over, you're probably not appending the tool_result before the next call. From Claude's view the tool never ran, so it asks again.
    Remember"tool_use" means run the tool and loop; "end_turn" means you're done. Nothing in the text overrides that.

    How do you safeguard against runaway loops?

    Layer a few cheap guards around the loop. stop_reason stays the normal way to stop; these guards only catch the cases where something has gone wrong.

    1. An iteration cap (the classic safety net)

    Count loop turns and stop at a sensible maximum, such as 25. The Agent SDK offers the same thing as a max-turns setting, so you don't have to hand-roll it.

    for turn in range(MAX_TURNS):        # e.g. 25
    resp = client.messages.create(...)
    if resp.stop_reason != "tool_use":
        return resp                   # normal exit: end_turn
    run_tools_and_append(resp)
raise LoopLimitReached()              # safety exit: something went wrong
    Exam point. Hitting the cap is a failure signal, not a finish line. Log it and escalate (for example to a human with a structured handoff) rather than quietly returning whatever you have.

    2. Budgets on tokens, cost and time

    Turn counts aren't the only thing that can run away. Whichever budget hits first stops the run:

    • a total token or dollar budget per task,
    • a wall-clock timeout (say, 5 minutes),
    • a limit on calls to expensive tools.

    3. Repeated-call detection

    Real runaway loops usually look like the same tool called with the same arguments again and again. Track the last few (tool, arguments) pairs. If the same one repeats three times, stop and investigate instead of spending more turns.

    4. Fix the causes, not just the symptom

    CauseWhat happensFix
    tool_result not appendedClaude never sees the result, so it keeps askingAlways append results with the matching tool_use_id
    Generic errors (“Operation failed”)Claude can't tell retryable from permanent, so it retries foreverStructured errors with errorCategory and isRetryable
    Vague tool descriptionsClaude cycles between tools looking for the right oneClear descriptions with boundaries
    Rule enforced only in the promptClaude keeps trying a forbidden actionA hook that blocks it and redirects

    What the exam tests

    Expect a question where an agent loops too long or burns tokens. The traps:

    • “Raise the iteration cap.” Treats the symptom and lets the loop run even longer.
    • “Make the cap the main stopping rule.” The anti-pattern from Rule 8.
    • “Tell Claude in the prompt to stop after a few tries.” Probabilistic and unreliable.

    The right answer usually fixes the cause: append tool results, structure the errors, or add a hook. The cap stays only as the safety net.

    Rememberstop_reason ends a healthy loop. A turn cap, budgets and repeat detection catch an unhealthy one. When a safeguard trips, treat it as a bug to fix, not a normal ending.

    Why do independent eyes review better? (Rule 9)

    Rule 9 has two parts. Don't let the author grade its own work: a fresh Claude instance reviews better than the one that produced the output. And don't review everything in one gulp: big reviews work better as focused passes plus one pass that looks across them.

    Part 1: Why self-review fails

    When a session writes code, its context holds all the reasoning behind it: “I'll skip the null check because this field is always set.” Ask that same session to review the code and it re-reads its own reasoning and agrees with itself. It's why you can't proofread your own essay right after writing it: you see what you meant, not what's on the page.

    A separate instance starts with only the code and the review criteria. It doesn't know why each choice was made, so it has to check whether each choice is actually right.

    Example 1: CI code reviewA Claude Code session builds a checkout feature. The pipeline asks the same session to review the PR, and it approves a bug where a coupon can push the total below zero.

    Right fixRun the review in a new, independent session that gets the diff, CLAUDE.md standards and review criteria, but not the generating conversation.

    Tempting distractor“Ask the same session to review again, more carefully,” or “add ‘be very critical’ to the prompt.” Same biased context, louder instructions.

    Example 2: Data extractionOne instance extracts invoice fields. You want to catch its errors.

    Right fixA second instance checks the extraction against the source document, paired with code-level checks such as calculated_total vs stated_total.

    Tempting distractorAsk the extracting instance “are you sure?”

    Part 2: Why one big review fails

    Give Claude a 20-file PR in one pass and its attention spreads thin: deep comments on the first few files, shallow or missed issues in later ones, and feedback that contradicts itself. This is attention dilution. A bigger context window doesn't fix it; the model can fit all 20 files, it just doesn't attend to them evenly.

    1. Per-file passes: review each file on its own, with full attention, for local bugs.
    2. One cross-file integration pass: look only at how files interact: data flowing between them, interface mismatches, a signature changed in one file but not in its callers.

    Example 3: The 20-file PRDevelopers complain the review bot misses bugs in later files and contradicts itself.

    Right fix20 per-file passes, then one cross-file integration pass.

    Tempting distractor“Increase max_tokens,” “use a larger context window,” or “run the full-PR review twice and keep findings both report.”

    Example 4: The bug only integration catchesorders.py changes get_total() to return cents instead of dollars. Each file looks fine on its own.

    Why both passesOnly the cross-file pass notices that invoice.py still treats the value as dollars: a 100x billing error.

    How it shows up on the exam

    Question saysAnswer
    “The session that wrote the code reviewed it and missed bugs”Independent instance without the generator's context
    “Review of a large PR is inconsistent, shallow on later files”Per-file passes plus a cross-file integration pass
    “Each file looks correct but the system breaks”The cross-file integration pass
    “Self-review isn't catching errors; one option is ‘review twice’”Reject it: same context, same blind spots
    RememberThe author can't see its own blind spots, so use a fresh reviewer. Big reviews get one focused pass per file, then one pass to see how the pieces fit.

    How do you protect what matters in context? (Rule 10)

    Claude only knows what's in its context window right now. In long conversations and multi-agent systems, that window fills with noise, gets summarized, and gets passed between agents. Every step can quietly lose the one detail that matters. Rule 10 means deciding what must survive and protecting it on purpose.

    TechniqueProtects against
    Case-facts block: exact facts pinned to every prompt, outside summarized historySummaries blurring “$1,247.50 by Friday” into “wants a refund”
    Trim tool output: keep only the fields that matter, ideally in code45-field lookups crowding out the conversation
    Key summary first, clear headers“Lost in the middle”: models attend most to the start and end of long inputs
    Provenance: claim-to-source mappings and dates through every hand-offCitations disappearing; old data read as a contradiction

    Simple scenarios

    1. The vanishing refund amountTurn 3: “I was charged $1,247.50 twice for order 88213, and the agent promised a refund by Friday.” By turn 40, older turns are summarized as “Customer had a billing issue,” and the agent asks the customer to repeat everything.

    FixExtract the facts into a block attached to every prompt and never summarized:

    CASE FACTS
order: 88213 | duplicate charge: $1,247.50 | refund promised: by Fri Nov 13
status: refund pending | customer ID: C-55102 (verified)

    Tempting distractor“Use a bigger context window” or “summarize less often.”

    2. The bloated lookupEvery lookup_order call returns 45 fields (warehouse codes, internal SKUs, audit timestamps). After four lookups, most of the context is fields nobody asked about.

    FixA PostToolUse hook keeps only order ID, status, amount, dates and items. Deterministic, and no wasted tokens.

    Tempting distractor“Tell Claude to ignore irrelevant fields.” They still take up the space.

    3. The forgotten middleSynthesis receives results from 12 research subagents in one long input. Findings from subagents 5 to 8 keep getting left out.

    FixPut a short key-findings summary at the top, then each subagent's results under a clear header.

    Tempting distractor“Shuffle the order each run” or “cut to three subagents.”

    Complex scenarios

    4. Multi-issue support session ending in escalationOver 50 turns a customer raises a duplicate charge, a damaged item, and an address change. The agent resolves two; the customer then asks for a human about the third.

    What has to surviveTrack facts per issue (“charge: refunded”, “damage: replacement shipped”, “address: blocked, item in transit”) plus every promise with its date. The human gets a structured handoff built from those facts (customer ID, each issue and status, what was tried, recommended next step), not the raw transcript. The hard part: facts change, so the block must be updated, not only appended to, or the human sees stale information.

    5. Multi-agent research with “conflicting” numbersSubagent A finds “EV market share: 18%” in a 2023 report; subagent B finds 24% in a 2025 report. Synthesis writes “Sources disagree (18% vs 24%).” There's no disagreement: the share grew. The dates were dropped between agents.

    FixEach subagent returns structured claims with source, published and excerpt; the coordinator passes them through intact, and synthesis reports a trend. If two 2025 figures truly disagreed, report both with sources rather than averaging or picking one.

    Tempting distractorAverage the two numbers, or keep whichever looks more recent without checking dates.

    6. Three-hour codebase explorationEarly on, Claude correctly identifies LedgerReconciler and RefundGateway. Two hours later it says things like “this typically uses a service layer.” It has lost the specifics.

    Fixes, in combinationCombine: a scratchpad file (findings.md) re-read before each answer; subagents for verbose digging that return summaries; phase summaries injected into the next phase; /compact only after key facts are saved; and a manifest for crash recovery.

    Tempting distractorKeep going in the same session, or restart and re-read the whole codebase.

    Where it can go wrong

    These failures happen even when you think you've followed Rule 10.

    1. A stale case-facts block. “Refund pending” is never updated to “refund issued.” Protected facts that are confidently wrong are worse than missing ones.
    2. Storing interpretations instead of facts. “Customer is angry and probably exaggerating” isn't a fact. Store what was said and verified; opinions in the block bias every later turn.
    3. Over-trimming. The hook drops delivery_date because it usually doesn't matter, then a return-window question arrives. Trim to what tasks need, and revisit when new task types appear.
    4. Trimming in the prompt instead of code. “Ignore irrelevant fields” still pays for the tokens. Trimming belongs in a hook or in the tool's response design.
    5. A wrong or lossy summary at the top. First position gives it extra weight. If it drops a caveat (“only in a sample of 40 patients”), you've amplified the error.
    6. A case-facts block that bloats. If every detail goes in, it becomes the new noise. Keep only facts that change decisions.
    7. Dropping provenance during “cleanup.” A step turns structured claims into tidy prose; sources vanish until someone asks where 24% came from.
    8. Compacting before saving. Running /compact before findings are in a scratchpad can lose them for good.
    9. A scratchpad nobody re-reads. Writing findings down only helps if the agent is told to consult them.
    10. Sensitive data in protected context. A block pinned to every prompt repeats card numbers or IDs in every call, log and handoff. Protect only what the task needs and mask the rest (last four digits). Not the exam's focus, but critical in regulated systems.

    Question saysAnswer

    “Tool results return many fields; context fills quickly”Trim to relevant fields (a hook)
    “Findings from the middle of the input are omitted”Key summary first, clear section headers
    “Report cites nothing” / “attribution lost”Claim-to-source mappings preserved through every step
    “Figures flagged as contradictory but from different years”Require publication or collection dates
    “Answers become vague in a long exploration session”Scratchpad, subagents, phase summaries, /compact

    Reject: “use a bigger context window,” “summarize more aggressively,” and “tell Claude to remember.” None of these protects anything.

    RememberDecide what must survive (facts, sources, dates) and keep it where every prompt can see it. Trim noise in code, put what matters first, and keep the protected facts current.

    What does “spawning” a subagent mean?

    Spawning means creating and starting a new subagent: launching a fresh worker to handle one job. The coordinator is running, decides it needs help, and spins up a helper with its own instructions.

    “Subagents are spawned via the Task tool”

    There's no special command for creating helpers. The coordinator uses a tool, the same way it would call lookup_order or web_search. That tool is named Task.

    Coordinator's response:
  tool_use: Task
    subagent: "web_researcher"
    prompt:   "Find 2025 data on EV market share. Return claims with source URLs and dates."

    The SDK starts a web_researcher subagent with that prompt, lets it work, and returns its final answer to the coordinator as the tool result. To the coordinator, it called a tool and got a result back; the “tool” just happened to be a whole agent.

    “The coordinator's allowedTools must include "Task"”

    Every agent has a list of tools it may use. If "Task" isn't on the coordinator's list, it can't spawn anyone and ends up doing everything itself.

    Classic exam question. “The coordinator never delegates to subagents. Why?” Answer: "Task" is missing from its allowedTools.

    “Each subagent type is an AgentDefinition”

    Before anything runs, you define the kinds of helpers available, like job descriptions on file:

    AgentDefinition fieldExample for web_researcher
    Description“Searches the web for current data and returns cited claims”
    System prompt“You are a research assistant. Always include source URLs and publication dates.”
    Toolsweb_search, fetch_page only

    The coordinator uses each definition's description to pick the right helper for a subtask, the same way tool descriptions help Claude pick tools.

    “Subagents do not inherit the parent's history or memory”

    Each spawned subagent starts blank. It knows its AgentDefinition plus the prompt from the Task call, and nothing else, so that prompt must contain everything it needs. See Can the synthesis agent read the coordinator's history?

    The analogy

    ConceptEveryday equivalent
    AgentDefinitionA job description on file
    Spawning with TaskHiring a contractor for one assignment and emailing the brief
    allowedTools includes "Task"The manager has permission to hire
    Doesn't inherit historyThe contractor knows only what's in the brief

    Bonus: parallel spawning

    The coordinator can spawn several subagents at once by putting multiple Task calls in a single response, rather than one per turn. Exam distractors for “make them run in parallel” include the Batch API and fork_session; neither is right.

    RememberSpawning = calling the Task tool to start a fresh helper from its AgentDefinition. No "Task" in allowedTools, no helpers. Helpers know only their brief. Several Task calls in one response run in parallel.

    Why use a programmatic prerequisite instead of a prompt?

    Prompts make the right order likely; code makes the wrong order impossible. This is Task 1.4, and it's Rule 1 applied to the order of steps.

    “Some step orders are business-critical”

    In many workflows, step B is only safe if step A already happened. Get the order wrong and the damage is real.

    Must happen firstBefore this
    Verify the caller's identity (get_customer)Issue a refund (process_refund)
    Confirm the account ownerChange the email or password on file
    Get manager approvalPay an invoice over $10,000

    “Prompt guidance has a non-zero failure rate”

    You can write: “Always call get_customer to verify identity before calling process_refund.” Claude follows it most of the time. But a prompt is guidance, not a guarantee. Some conversations will skip the step: unusual phrasing, a customer who sounds very confident (“I'm John Smith, just refund it”), or a long conversation where the instruction gets less attention.

    Even a 1% failure rate is 100 wrongly refunded accounts per 10,000 chats. For money or security, that's unacceptable.

    “Programmatic prerequisites do not”

    A programmatic prerequisite is a check in your code that makes the wrong order impossible, whatever Claude decides:

    def process_refund(customer_id, amount, session):
    if not session.verified_customer_id:
        return {"isError": True, "errorCategory": "validation",
                "message": "Verify the customer with get_customer before refunding."}
    if customer_id != session.verified_customer_id:
        return {"isError": True, "errorCategory": "permission",
                "message": "Refund must match the verified customer."}
    # only now does the refund actually run

    If Claude tries process_refund too early, the code blocks it with a clear error, and Claude goes back and calls get_customer. The skip rate is now zero. A PreToolUse hook that blocks process_refund until verification is recorded does the same thing in a different place.

    The analogy

    A prompt is a sign on the door: “Staff must badge in before entering the vault.” Most people comply. A programmatic prerequisite is the lock: the door won't open without a badge. For a vault, you want the lock.

    How it shows up on the exam

    “The agent calls process_refund before get_customer in 12% of conversations, causing refunds to the wrong accounts. What's the best fix?”

    OptionVerdict
    Add a bold system-prompt rule to always verify firstWrong: still probabilistic
    Add few-shot examples showing verification firstWrong: still probabilistic
    Add a routing classifierWrong: controls which tools exist, not their order
    Programmatic prerequisite that blocks process_refund until get_customer returns a verified IDRight: guarantees the order

    How to tell you need it: the mistake would cost money, break security or violate compliance, and the question says it fails some percentage of the time. Then the answer is code (a gate or hook), not more prompting.

    RememberPrompts make the right order likely; code makes the wrong order impossible. When the order matters, use code.

    How do hooks work, and when should you use them?

    Hooks are your code that runs automatically at fixed points in Claude's agent loop. Claude doesn't choose whether a hook runs; it runs every time. That's why hooks are how you guarantee a rule instead of asking for it.

    Where hooks sit

    Claude requests a tool
        │
   ┌────▼─────┐   allow / block / modify / redirect
   │PreToolUse│ ◄── your code inspects the CALL before it runs
   └────┬─────┘
        │
   tool runs
        │
   ┌────▼──────┐  clean / trim / normalize / mask
   │PostToolUse│ ◄── your code inspects the RESULT before Claude sees it
   └────┬──────┘
        │
 Claude reads the result

    Other hook points exist (when a session starts, when the user submits a prompt), but the exam focuses on these two.

    What each hook can do

    PreToolUse: sees the call before it runsPostToolUse: sees the result before Claude does
    Allow the call throughNormalize formats (Unix timestamps to ISO dates, codes to labels)
    Block it, with a reason Claude can readTrim 45 fields down to the 5 that matter
    Modify the argumentsMask sensitive data (card number to •••• 4417)
    Redirect: block and say what to do insteadLog for auditing

    Examples

    1. Refund limit (PreToolUse: block and redirect)Policy: refunds over $500 need a human.

    How

    # simplified, illustrative
def pre_tool_use(tool_name, args):
    if tool_name == "process_refund" and args["amount"] > 500:
        return block(reason="Refunds over $500 need human approval. "
                            "Call escalate_to_human with the case summary.")
    return allow()
    Claude reads the reason and calls escalate_to_human. No prompt wording can make a $600 refund go through.

    2. Messy dates from three systems (PostToolUse: normalize)The orders, shipping and returns tools return dates in three formats.

    HowA hook converts them all to ISO 8601 before Claude reads them, so return-window math is always right.

    3. Bloated lookups (PostToolUse: trim)lookup_order returns 45 fields.

    HowThe hook keeps order ID, status, amount, dates and items: Rule 10 done in code.

    4. Dangerous commands in Claude Code (PreToolUse: block)An agent with Bash access could run destructive commands.

    HowA hook on the Bash tool blocks commands matching rm -rf or git push --force to the main branch, whatever the conversation says.

    5. PII masking (PostToolUse: mask)Customer records include full card numbers.

    HowA hook masks them before they enter context, so they never appear in logs, summaries or handoffs. Critical in regulated environments.

    Hooks vs a check inside the tool

    The prerequisite FAQ put the verification check inside process_refund. Both approaches are deterministic and both satisfy Rule 1. The difference is where the check lives:

    Check inside the toolHook
    WhereIn the tool's own codeAround every tool call, in one place
    Best whenThe rule belongs to that one toolThe rule spans many tools, or you don't own the tool (a third-party MCP server)
    Exampleprocess_refund checks verificationOne hook masks PII from every tool's results

    On the exam, either counts as “programmatic.” What matters is choosing code over prompts.

    When not to use a hook

    Hooks suit rules a program can check: an amount over $500, a missing field, a command matching a pattern. They're bad at judgment calls:

    • “Escalate when policy is ambiguous” needs reasoning: explicit criteria and few-shot examples in the prompt.
    • “Be empathetic with frustrated customers” is tone: the prompt.
    • “Pick the right tool”: tool descriptions.
    Exam shortcut. Can you write the rule as an if statement? Then it's a hook. Does it need judgment? Then it's a prompt.

    Where hooks go wrong

    1. Blocking without a reason. A bare “denied” can make Claude retry the same call forever, a runaway loop. Always say why and what to do instead.
    2. Over-broad rules. A hook that blocks every rm also blocks rm temp.txt. Match precisely.
    3. Over-trimming. A PostToolUse hook that drops delivery_date breaks return-window questions later.
    4. Checking too late. Flagging a $600 refund in PostToolUse means the money already moved. Blocking belongs in PreToolUse.
    5. Using hooks for judgment. Pattern-matching angry words to force escalation is sentiment-based escalation, which the exam calls unreliable.

    Exam signals

    Question saysAnswer
    “Must never exceed / must always / compliance / slips X% of the time”PreToolUse hook (or prerequisite gate)
    “Tools return data in different formats”PostToolUse hook to normalize
    “Tool results are verbose and fill context”PostToolUse hook to trim
    “A refund over the limit was flagged after processing”Wrong hook point: move the check to PreToolUse
    An option says “add it to the system prompt” for a hard ruleReject: probabilistic
    RememberHooks are code that runs on every tool call: PreToolUse decides whether a call may happen; PostToolUse cleans what comes back. If a rule can be written as an if and must never be broken, it belongs in a hook.

    What is adaptive decomposition (vs prompt chaining)?

    Both are ways to break a big task into steps (Task 1.6). The difference is when you decide the steps.

    Prompt chainingAdaptive decomposition
    Steps decidedUp front, before startingAs you go, based on what each step finds
    PlanFixed, the same every timeChanges as findings come in
    Best forPredictable tasks with known stepsOpen-ended investigation
    AnalogyA recipeA detective following clues

    Prompt chaining: the fixed plan

    You know the steps before starting and run them in order every time. Reviewing every PR:

    1. Check security.
    2. Check correctness.
    3. Check test coverage.
    4. Write the summary.

    Every PR goes through the same four steps: predictable, consistent, easy to debug.

    Adaptive decomposition: the plan that evolves

    You can't know the steps in advance, because each finding decides the next move. “Checkout got twice as slow last week. Why?”

    1. Map the system: what does checkout touch? Payments, inventory, pricing, tax.
    2. Find high-impact areas: what changed last week? A pricing deploy and a new tax provider.
    3. Prioritize: investigate the tax provider first (new, external, likely slow).
    4. Adapt: tax calls look fine, but the pricing service now hits the database once per cart item. New subtask: check that query.
    5. Keep adapting until the cause is found.

    No fixed recipe could have predicted step 4; the plan was rewritten because of what was discovered.

    Pattern to memorize: map → prioritize → investigate → adapt.

    A useful combination

    Large code reviews mix both ideas: a fixed chain of per-file passes, then one cross-file integration pass (Rule 9). That's still prompt chaining, because the steps are known up front. Adaptive decomposition is only for when the next step genuinely depends on what you find.

    How it shows up on the exam

    Question saysAnswer
    “Review every PR for security, style and tests”Prompt chaining
    “Investigate why X broke / is slow”Adaptive decomposition
    “Add test coverage to a large legacy codebase”Adaptive: map, find high-risk areas, plan, adapt
    “Review a 14-file PR”Chaining: per-file passes plus a cross-file pass

    Traps:

    • A fixed pipeline for an investigation (“analyze all 40 services alphabetically”): wastes effort and ignores clues.
    • One giant prompt (“here's the codebase and the latency graph, find the bug”): attention diluted, no structure.
    • Adaptive decomposition for a repeatable process: loses the consistency you need.

    How it relates to coordinator decomposition

    Coordinator decomposition is who breaks the task down: the coordinator, splitting work across subagents. Chaining vs adaptive is how it's broken down: a fixed plan or an evolving one. A coordinator can use either.

    RememberPrompt chaining is a recipe: same steps every time. Adaptive decomposition is detective work: map, prioritize, and let each finding decide the next step.

    Resume, fork or fresh start: which one, and what are the tricky questions?

    Three ways to continue earlier work (Task 1.7). The exam tests whether you pick the right one.

    OptionWhat it doesAnalogy
    Resume (--resume <session-name>)Continues a named session with its full historyReopening a saved document
    Fork (fork_session)Copies a session's state into an independent branch“Save as” a copy, or a git branch
    Fresh start + summaryNew session with a structured summary injected at the startA new document plus a briefing memo

    Resume

    claude --resume payments-investigation

    Same conversation, same tool results, same decisions. Naming sessions matters: with several investigations open, the name gets the right one instead of “the most recent.”

    • Use it when the earlier context is still mostly true.
    • The catch: the session remembers old tool results. If files changed, tell it what changed: “Since yesterday, refund.py, ledger.py and config.yaml were modified. Re-read them before continuing.”

    Fork

              analysis of legacy payments module
                       │
          ┌────────────┴────────────┐
       fork A                     fork B
  "refactor with              "refactor with
   strategy pattern"           event sourcing"
          │                         │
     try it, evaluate          try it, evaluate
    • Use it when comparing alternatives from the same starting point, without redoing the analysis.
    • Why not try both in one session? Attempt B would remember attempt A: biased thinking, cluttered context. Forks keep each attempt clean.

    Fresh start + summary

    A new session given key findings, decisions, open questions and which files matter.

    • Use it when earlier tool results are stale: many files changed, or the old session has drifted.
    • Why not resume? Outdated tool output gets treated as current. A clean summary carries only what's still true.

    The decision guide

    Is the old context still mostly accurate?
├── Yes → RESUME (and tell it exactly what changed)
└── No  → FRESH START with a structured summary

Want to compare two approaches from the same baseline?
└── Yes → FORK

    Tricky questions you might see

    1. A few files changedYou resume a named investigation. Overnight a teammate edited 3 of the 40 files you analyzed; answers now describe old code.

    RightResume and tell the session which 3 files changed so it re-reads them.

    Distractors
    • “Start fresh and redo the analysis”: throws away 37 files of valid work.
    • “Fork the session”: the fork copies the same stale context.
    • “Run /compact”: shrinks context but doesn't refresh stale facts.

    2. Almost everything changedSame setup, but a large refactor touched about 80% of the files.

    RightFresh start with a structured summary of findings that are still valid.

    Distractors
    • “Resume and list every changed file”: most old tool results are now wrong.

    The trickQuestions 1 and 2 look nearly identical. The deciding detail is how much changed.

    3. Compare two approachesAfter a long analysis, you want to try two refactoring strategies and compare.

    RightFork from the shared analysis.

    Distractors
    • “Two new sessions that each redo the analysis”: wasteful.
    • “Resume and try one, then the other”: the second attempt is biased by the first.
    • “Plan mode”: designs one approach before editing; doesn't run two in isolation.

    4. Fork vs parallel subagentsTwo things sound like “run in parallel.”

    RightFork = alternatives to the same problem (“which approach is better?”). Parallel Task calls = different parts of one task (“search news, papers and patents”). Comparing options: fork. Splitting work: parallel subagents.

    Distractors
    • Using fork to split one task into parts.
    • Using parallel subagents to compare two strategies.

    5. “Forks share updates”A distractor claims a fix in branch A automatically appears in branch B.

    RightFalse. Forks are independent; that's the point of forking.

    Distractors
    • Any option that relies on branches staying in sync.

    6. The session has gone vagueThree hours in, Claude refers to “typical patterns” instead of the classes it found.

    RightFresh start with a summary, or a scratchpad, subagents and /compact (Task 5.4).

    Distractors
    • “Resume it tomorrow”: the degradation comes with it.

    7. Decisions valid, tool output staleYesterday's architecture decisions stand, but the code they were based on was reworked.

    RightFresh start, injecting a summary of the decisions without the stale tool output.

    Distractors
    • “Resume, since the decisions are still valid.”

    The trickJudge “mostly valid” on the tool results, not just the decisions. Old file reads are what mislead Claude.

    8. Crash recovery in a multi-agent systemA coordinator with five subagents crashes mid-job.

    RightEach agent exports state to a known location; the coordinator loads a manifest on restart (Task 5.4).

    Distractors
    • “--resume the coordinator session”: restores only the coordinator. Subagents start blank, so their progress is lost.

    9. Which session?Several investigations are open; continue the payments one.

    Right--resume payments-investigation, a named session.

    Distractors
    • “Continue the most recent session”: might be a different investigation.

    Signal words

    Question saysAnswer
    “pick up where we left off,” “a few files changed”Resume, and tell it what changed
    “most files changed,” “tool results outdated,” “session degraded”Fresh start with a structured summary
    “compare,” “try two approaches,” “same starting analysis”Fork
    “split the work,” “different sources at the same time”Parallel subagents, not fork
    “crashed,” “restore all agents”State exports plus a manifest
    RememberResume when the old context is still true (and say what changed). Start fresh with a summary when it's stale. Fork to compare alternatives from the same starting point.

    How do slash commands and skills work?

    Both package a reusable instruction in Claude Code so you don't retype the same long prompt (Task 3.2). The exam tests two things: where the file goes (personal or team) and which one to use (command, skill or CLAUDE.md).

    Slash commands

    A slash command is a saved prompt in a Markdown file. The file name becomes the command name: .claude/commands/review.md becomes /review.

    ---
description: Review the current changes against team standards
argument-hint: [file or folder to review]
allowed-tools: Read, Grep, Glob
---
Review $ARGUMENTS for:
1. Bugs that cause wrong results
2. Security issues
3. Missing tests
Skip style and formatting. Report each finding as: file, line, issue, suggested fix.

    Typing /review src/payments sends that prompt with $ARGUMENTS replaced by src/payments. A command runs only when someone types it.

    Skills

    A skill is a folder with a SKILL.md file, plus optional scripts, templates or reference files. It packages a procedure Claude can use when the task calls for it.

    .claude/skills/release-notes/
├── SKILL.md
├── template.md
└── format_changelog.py
    ---
name: release-notes
description: Draft release notes from merged PRs since the last tag. Use when asked for release notes or a changelog.
context: fork
allowed-tools: Bash, Read
argument-hint: [version number]
---
1. Find the last git tag.
2. List PRs merged since then.
3. Group them into Features, Fixes and Breaking changes using template.md.
    • It can bundle files: templates, scripts and reference docs live in the same folder.
    • Claude can pick it up on its own. The description says when the skill applies, just as a tool description says when to use a tool. A vague description means the skill gets used at the wrong times, or never.

    The three frontmatter fields the exam names

    FieldWhat it doesWhen the exam wants it
    context: forkRuns the skill in an isolated sub-agent; only its final result returns to the main conversationThe skill produces pages of exploratory output that clutter the chat
    allowed-toolsRestricts which tools the skill may use“This skill must only read files, never run shell commands”
    argument-hintShows what argument is expected, prompting for it if missing“Developers keep invoking /triage without the ticket ID”

    context: fork is the same idea as a spawned subagent: the noisy work happens in its own context and you get back a summary, which protects your main context (Rule 10).

    Where the files go: team vs personal

    Team (shared through git)Personal (only you)
    Slash commands.claude/commands/ in the repo~/.claude/commands/
    Skills.claude/skills/<name>/SKILL.md in the repo~/.claude/skills/<name>/SKILL.md
    Same pattern as CLAUDE.md and MCP: the repo's .claude/ folder is the team's; ~/.claude/ in your home folder is yours.

    Commands vs skills vs CLAUDE.md

    All three hold instructions. The difference is when they load:

    CLAUDE.mdSkillSlash command
    LoadsAlways, every sessionOn demand, when relevant or invokedOnly when typed
    Best forUniversal standardsMulti-step procedures used sometimesA prompt you trigger deliberately
    Example“Use TypeScript strict mode”“Draft release notes,” “run a security audit”/review, /deploy-check

    The test: applies to every task? CLAUDE.md. A procedure for some tasks? A skill. Want to trigger it by name? A command. A 12-step procedure in CLAUDE.md eats context in every session.

    In recent Claude Code versions commands and skills overlap more (a skill can also be invoked by name with a slash). For the exam, keep the distinction: CLAUDE.md is always loaded, skills are on demand.

    Tricky questions you might see

    1. “Every developer who clones the repo”You want /review available to the whole team.

    Right.claude/commands/review.md, committed to the repo.

    • “A commands array in .claude/config.json”: this doesn't exist. A classic invented distractor.
    • “Define it in CLAUDE.md”: CLAUDE.md holds instructions, not command definitions.

    2. A personal variantA developer wants their own version of the team's /pr-summary skill.

    RightCopy it into ~/.claude/skills/ under a different name and customize it there.

    Distractors
    • “Edit the project skill and don't commit”: fragile, and easy to commit by accident.

    3. The output is flooding the conversationA codebase-survey skill dumps hundreds of lines into the chat.

    Distractors

    4. “It must never run Bash”A skill should only read files.

    Rightallowed-tools: Read, Grep, Glob.

    6. A 12-step procedure in CLAUDE.mdThe team's release procedure lives in CLAUDE.md and runs once a sprint. Sessions feel bloated.

    Distractors

    Which CLAUDE.md wins: project level or folder level?

    The folder-level (subdirectory) CLAUDE.md wins when the two conflict. The more specific scope wins.

    repo/
├── CLAUDE.md              ← project level: "Use 2-space indentation"
└── legacy/
    └── CLAUDE.md          ← folder level: "Use 4-space indentation"

    legacy/billing.py, with project rule “write tests for every change”Tests still requiredNo conflict, so the project rule still applies inside legacy/

    Both files load; only the conflicting instruction is overridden. They are never averaged: 2 and 4 never become 3. The folder file loads when Claude works on files in that folder, so it affects only that part of the codebase.

    The full order, general to specific

    enterprise → user (~/.claude/CLAUDE.md) → project (./CLAUDE.md) → subdirectory (legacy/CLAUDE.md)

    What are Grep and Glob (and Read)?

    Three of Claude Code’s built-in tools for looking at a codebase. They’re read-only: none of them can change a file, which is why they run without asking for approval.

    ToolFinds things byQuestion it answersEveryday analogy
    GlobFile name / path“Which files exist that match this pattern?”Searching a filing cabinet by folder labels
    GrepFile contents“Which files contain this text?”Ctrl+F across every document at once
    Read— opens one file“What’s in this file?”Opening the document and reading it

    Glob: find files by name

    Glob matches file paths with wildcard patterns. It never looks inside files. * means “anything in this folder”; ** means “any number of folders deep.”

    PatternMatches
    *.pyPython files in the current folder
    **/*.test.tsxEvery .test.tsx file in any folder, at any depth
    src/**/config*Anything starting with “config” anywhere under src/
    **/DockerfileEvery Dockerfile in the repo

    These are the same globs used in .claude/rules/ paths: frontmatter (Task 3.3).

    Grep: find text inside files

    Grep searches file contents for a word or pattern and returns the matching lines and files.

    SearchFinds
    processRefundEvery place the function is defined or called
    "Connection refused"Where an error message is produced
    import stripeEvery file that uses the Stripe library
    TODO|FIXMEEvery to-do comment

    Read: open one file

    Read returns a file’s full contents so Claude can follow the actual logic. Its partners for changing files, Edit and Write, need approval.

    How they work together

    Exploring an unfamiliar codebase: “how do refunds work?”

    1. Glob **/*refund* → finds refund_service.py, refund_api.py, test_refund.py.
    2. Grep processRefund → it’s called from checkout.py and admin.py.
    3. Read refund_service.py → follow the actual logic.
    4. Repeat: Grep for what it imports, Read those files.

    This is the Task 2.5 pattern: Grep to find entry points, Read to follow imports and trace flows. Build understanding step by step instead of reading every file up front.
